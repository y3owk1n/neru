# Overlay adapters — contracts

These rules fail silently at runtime, not at compile time; read before editing.

- **Threading is platform-asymmetric.** macOS serializes through the Obj-C bridge (`dispatch_async` to the main thread); Linux must serialize itself — Cairo/X11/Wayland calls are not thread-safe (`linux/manager.go`).
- **A draw may block, and must never be called while the mode handler's lock is held.** Draws dispatch asynchronously on macOS but hold `renderMu` synchronously on Linux; that asymmetry is deliberate, so callers must assume the blocking case. The mode handler computes what to draw under its lock and draws after releasing it (`internal/app/modes/AGENTS.md`); the exceptions are the whole hints surface — the update callback (`hintdraw.go`), the theme refresh and the search input, which now go through the port but still draw under the handler lock, and whose first draw per activation runs the entire `ShowFrame` transition (resize, show, switch) under it — both grid surfaces, whose activations, redraws and per-keystroke updates all run under it (#1211) — and mode teardown, which hides indicators and clears the frame under it. `h.mu` → `renderMu` is therefore a real edge, and safe only while the reverse never exists: nothing holding `renderMu` may call into the app layer or publish to a subscriber that takes `h.mu`.
- **Lock topology is deliberate.** The manager owns `renderMu`, held across synchronous draws; animation goroutines lock it via `sharedOverlay`. The mouse-action indicator owns an independent X11/Wayland connection and must **not** share `renderMu` — it has its own `indicatorMu` / `indicatorRenderMu`.
- **Surface primitives split** (#1177): layout, animation, offsets, and label logic live once on `sharedOverlay`; only buffer management, HiDPI scale, and window lifecycle go behind `overlaySurface`. Shared code never touches cgo — primitives take Go types and own their C marshaling, including CString lifetimes.
- **Backend exported methods are thin nil-guarded delegates** — a promoted method through a nil backend pointer panics before any receiver guard runs. `Get()` must never return a typed nil, or every `!= nil` guard downstream silently passes (`backend_linux.go`).
- **`originOffset` applies selectively**: grid, recursive-grid, and hints arrive screen-local and get the offset — including the virtual pointer, which rides the recursive-grid frame. Absolute draws (the cursor-tracking mode and sticky-modifiers indicators, monitor_select, click indicator) must not.
- **The overlay owns the Styles it hands out** (#1207): `StyleResolver` (`style.go`) is the only place the *drawn* styles — hints, hint search input, grid, recursive grid, monitor-select, virtual pointer — are built from `config + theme`. It resolves on a config reload or a theme change, never per draw, and `Apply` is also the one notification that hands a new configuration to the render components — one call to `ConfigureComponents`, because the manager knows which components it built. **A configured font family is a resolved one**: every family the resolver hands out has been through `ports.ResolveFont` (#1305), including the two that reach a component as configuration rather than as a Style — the virtual pointer's, which travels as `manager.PointerAppearance` and is substituted into the `config.VirtualPointerUI` the grid, recursive-grid and virtual-pointer components are handed, and monitor-select's subtitle family, whose "unset means the label's" fallback is applied *before* resolution because the resolver answers an empty name with the platform sans. So no backend or render component calls the resolver on a family it was given, and none may resolve per draw — the pointer redraws on every cursor move. Read one via `overlay.ResolvedStyle(source)`; a `BuildStyle` call anywhere else re-creates the fan-out this replaced, and a missed call site leaves an overlay in the previous theme's colours. **Still outside it**: the mode-indicator, sticky-indicator and virtual-pointer overlays hold their own `ThemeProvider` (handed to them at construction) and resolve their colours at draw time, and the click indicator's style is built in `app/services/action_service.go`. The pointer drawn on a grid surface is inside it: `UpdateGridPointer` meets a position from the caller with the resolved virtual-pointer Style here (#1211), so no mode reads a style to move it.
- **The overlay builds its own render components** (#1209): `Base.BuildComponents` (`manager/components.go`) constructs them from a `ComponentSpec` — configuration, theme provider, logger, window handle, headless verdict — and keeps them; the app hands over the first two and reads nothing back. The built set was returned for the "was this overlay built at all" guards in `app/lifecycle.go`; those went with #1213, because a screen change now hands over a Frame and every draw already answers "never constructed" here. No app-layer type names a render component. The window handle and the headless verdict come from the backend's own `BuildComponents`, which is the only reason that delegate exists: a `Base` cannot see the surface, and a `Base` method cannot dispatch to a backend's override (darwin's `UseVirtualPointerOverlay` propagates screen-share state, so darwin re-applies it after the build). A backend delegate must nil-guard its receiver like every other exported method here. A failed component is logged and left nil; only the virtual pointer fails the build, because that is the one the app's startup phase treated as fatal.
- **An Indicator is driven through the port, never through its render object** (#1208): `ShowIndicator` / `HideIndicator` / `ResizeIndicatorToActiveScreen` take a `ports.Indicator`; `manager.Base` resolves it to a render component and answers "never constructed" itself, so no caller nil-checks one. `HideIndicator` owns clearing as well as hiding — on macOS the component has its own window, on Linux it is a badge painted on the shared surface and hiding it means erasing that rectangle (`linux/manager.go` overrides it for exactly that). The app side is one service per indicator in `app/services/{modeindicator,stickyindicator,virtualpointer}`, all built on `app/services/indicator`.
- **A mode hands over a Frame; this package owns the sequence that realises it** (#1210): `Adapter.ShowFrame` (`adapter.go`) is the only place `ResizeToActiveScreen` → `Show` → `SwitchTo` → draw exists, and `ClearFrame` the only place the leaving half does. `RedrawFrame` draws a frame already on screen and deliberately skips the window sequence — hint labels narrow on every keystroke, and a `Show` per keystroke is a `dispatch_async` of window level, collection behaviour and ordering that ADR 0003 rules out. A `ports.Frame` carries domain values only: converting them to render models and meeting them with the resolved Style happens here and nowhere upstream, and `internal/architecture/overlay_frame_test.go` fails the build if a Frame field is typed from anything but the standard library or `internal/domain/`. Every surface is a frame since #1212, and the window sequence is the one thing a frame varies: `drawsOnSharedWindow` says no only for monitor-select, whose panels are per-display windows on macOS and whose Linux draw shows the spanning window itself — bringing an empty always-on-top window up behind them would put something on screen that nothing draws into. Scroll draws nothing and still says yes, because on Linux the mode and sticky-modifier badges are painted on that surface: a hidden shared window is an invisible indicator, and answering from macOS's one-window-per-indicator model would strand a Linux user in scroll mode with no indicator after a monitor move. Drawing the picker stays an optional capability reached by type assertion (`manager.MonitorSelector`), asserted in `Adapter.drawMonitorSelect` rather than by widening the port; a backend without it reports `CodeNotSupported` and the mode refuses to activate. `ClearFrame` also takes the panels down — they are not on the shared surface, so clearing that surface leaves them on screen — and `monitorSelectDrawn` is the second piece of screen state this package keeps, for the same reason `subgridDrawn` is the first.
- **Each grid surface says what its draw needs, and the updates stay calls** (#1211): a grid draw clears the surface when the frame is coming up or when a subgrid is on it — the backend's incremental path compares grids and cannot diff a subgrid away, and `Adapter.subgridDrawn` is the one piece of screen state this package keeps, because `ShowGridSubgrid` is what put it there. Clearing on every redraw instead would blink the mode and sticky-modifier indicators off the shared Linux surface until the next poll, on every theme change. A recursive-grid draw clears on the transition only, because that backend animates from the bounds it last drew: a fresh activation must not zoom out of the region the last one left, and a keystroke must. Everything a keystroke changes in grid mode stays a plain call by ADR 0003 — `UpdateGridMatches`, `SetGridHideUnmatched`, `ShowGridSubgrid`, `UpdateGridPointer` — and none of them builds a frame. Recursive grid has no incremental path: its keystroke redraws the whole surface, so it hands over a frame, and that costs one interface boxing per key (measured on #1211: grid narrowing unchanged in time and allocations, recursive grid +1 allocation of 128 B with no measurable time cost). The pointer stand-in a grid mode draws is **not** an Indicator — it belongs to the mode's own drawing, and `manager.Base` resolves the mode to a render component (`DrawGridPointer`/`HideGridPointer`) the way it resolves an indicator.
- **The hint search input's geometry is resolved here too** (#1210): `SearchInputLayout` travels with the Style, so a config reload moves the box and a draw does no configuration lookup; `searchInputFrame` places it against the screen the caller names and clamps it on. `HintSearchBounds` exists because the platform IME field has to sit over the same rectangle — asking beats deriving it a second time in the mode layer. Every anchor `config.SearchInputPositions()` declares has a branch there and an anchor outside it is refused, not approximated (#1329): `DrawHintSearch` warns and returns `CodeNotSupported` before drawing — the degradation `ports.OverlayPort` already documents for a search input that does not appear — and `HintSearchBounds`, which answers a rectangle and cannot report, answers the empty one, because the box the IME field would sit over was never drawn. The empty string is refused with the rest rather than settled to the default the way `hints.ui.placement` is: the validator refuses an unset position, so the only Style carrying one is a Style nothing resolved.
- **No app package imports this one** (#1213): the shared-infrastructure allowlist entry in `layering_test.go` is gone, so `internal/architecture` fails the build if one does again. Everything the app says to the overlay it says through `ports.OverlayPort` — frames and updates, plus the four calls that used to reach past it: `ApplyConfig` and `RefreshStyles` (the one notification a config reload or a theme change owes the resolver), `SetHiddenInScreenShare`, and `Destroy`. `overlay.Init` and the `OverlayManager` alias are named only by the composition root (`app/wiring.go`, `app/startup_phases.go`), which builds the backend and the adapter over it; `app.WithOverlayPort` replaces it wholesale, and a session that brings its own port builds no backend at all. The Linux keyboard grab is `SetKeyboardCaptureEnabled` on the port, answered here by asserting `manager.KeyboardCaptureController` on the backend — a plain method rather than a port-level capability, because asking is always safe and what confines the behaviour to Linux is the caller's gate on the **event tap**, not the overlay. The package singleton `Get()` is no longer reached from `app/modes`; its only remaining caller is the Linux event tap. `render/*` owns style and drawing only: the per-mode `Context` types that lived in `render/{hints,grid,recursivegrid}` were mode state, not render models, and moved to `internal/app/components/`. Optional backend capabilities are still reached by type assertion, not interface widening.
- **`manager.Interface` is wide on purpose, and internal.** It is the contract between this adapter and its backends, and narrowing it is not what the port work was for. No package outside this one implements it and none but the composition root names it (`app/wiring.go` aliases it to build the adapter over), the no-op manager that used to stand in for a display is gone from the shipped binary (#1213), and the headless base the adapter's own tests build fakes on lives in `headless_manager_test.go`.
