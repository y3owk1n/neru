# Overlay adapters — contracts

These rules fail silently at runtime, not at compile time; read before editing.

- **Threading is platform-asymmetric.** macOS serializes through the Obj-C bridge (`dispatch_async` to the main thread); Linux must serialize itself — Cairo/X11/Wayland calls are not thread-safe (`linux/manager.go`).
- **A draw may block, and must never be called while the mode handler's lock is held.** Draws dispatch asynchronously on macOS but hold `renderMu` synchronously on Linux; that asymmetry is deliberate, so callers must assume the blocking case. Windows sits between: a draw holds `renderMu` while it queues commands, and `Flush` hands the frame to the overlay UI thread and returns — painting and presenting happen there, and frames that pile up coalesce (`platform/windows/overlay.go`), so nothing on the keyboard hook's thread waits for pixels. The mode handler computes what to draw under its lock and draws after releasing it (`internal/app/modes/AGENTS.md`); the exceptions are the whole hints surface — the update callback (`hintdraw.go`), the theme refresh and the search input, which now go through the port but still draw under the handler lock, and whose first draw per activation runs the entire `ShowFrame` transition (resize, show, switch) under it — both grid surfaces, whose activations, redraws and per-keystroke updates all run under it (#1211) — and mode teardown, which hides indicators and clears the frame under it. `h.mu` → `renderMu` is therefore a real edge, and safe only while the reverse never exists: nothing holding `renderMu` may call into the app layer or publish to a subscriber that takes `h.mu`.
- **Lock topology is deliberate.** The manager owns `renderMu`, held across synchronous draws; animation goroutines lock it via `sharedOverlay`. The mouse-action indicator owns an independent X11/Wayland connection and must **not** share `renderMu` — it has its own `indicatorMu` / `indicatorRenderMu`. **Canceling an animation is the one thing that happens outside it** (#1490): `cancelAnimation` waits for a goroutine that takes `renderMu` on every frame, so every Linux manager method that stops one cancels *before* it takes the lock — and then re-reads the backend pointer under it, because the gap is where a `Destroy` lands. The corollary is that no repaint inside a backend may reach `clear()`, whose first act is that cancel; the ones that clear a surface they are about to redraw go through the `surfaceClear` primitive instead.
- **Surface primitives split** (#1177): layout, animation, offsets, and label logic live once on `sharedOverlay`; only buffer management, HiDPI scale, and window lifecycle go behind `overlaySurface`. Shared code never touches cgo — primitives take Go types and own their C marshaling, including CString lifetimes.
- **The Linux backends' exported methods live on `sharedOverlay`, and the manager's nil check is what makes calling one safe** (#1415, ADR 0010): eighteen of them — every draw plus `Hide`, `Clear`, `ClearRect`, `Flush`, `SetHideUnmatched`, `HideHintSearchInput`, `setOriginOffset`, and the pair grid mode's pointer stand-in travels on, `SetGridPointer` / `forgetGridPointer` (#1463) — are declared once and promoted into `x11Overlay` / `wlrootsOverlay`. Each guards itself with `sharedOverlay.drawable()` — is a surface wired, and does `alive()`, the question `overlaySurface` now declares and each backend answers against its own `raw`, still say the native handle is open — in place of the `o.raw != nil` prologue it used to carry. Only `Show`, `Resize` and `Destroy` stay per-backend, because only those three genuinely differ. A promoted method reached through a **nil** backend pointer panics on the promotion, before any receiver guard inside could run — so every dispatch in `linux/manager.go` nil-checks the pointer first, and reads it once (`cancelBackendAnimation`) rather than twice. Those checks are not an interface nobody wrote; ADR 0010 is why, and deleting one turns a silent no-op into a crash. The `!cgo` twins deliberately keep their methods per-backend: their constructors always return nil, so every body exists precisely to be reached on a nil receiver. `Get()` must never return a typed nil either, or every `!= nil` guard downstream silently passes (`backend_linux.go`).
- **`originOffset` applies selectively**: grid, recursive-grid, and hints arrive screen-local and get the offset — including the virtual pointer, which rides the recursive-grid frame and, since #1463, is painted into the grid's own repaint on Linux from the state `SetGridPointer` left, and the hint search badge, whose frame `searchInputFrame` placed against the screen the caller named. Absolute draws (the cursor-tracking mode and sticky-modifiers indicators, monitor_select, click indicator) must not. What decides it is where the coordinates came from, not whether the thing drawn is a badge.
- **The overlay owns the Styles it hands out** (#1207): `StyleResolver` (`style.go`) is the only place the *drawn* styles — hints, hint search input, grid, recursive grid, monitor-select, virtual pointer — are built from `config + theme`. It resolves on a config reload or a theme change, never per draw, and `Apply` is also the one notification that hands a new configuration to the render components — one call to `ConfigureComponents`, because the manager knows which components it built. **A configured font family is a resolved one**: every family the resolver hands out has been through `ports.ResolveFont` (#1305), including the two that reach a component as configuration rather than as a Style — the virtual pointer's, which travels as `manager.PointerAppearance` and is substituted into the `config.VirtualPointerUI` the grid, recursive-grid and virtual-pointer components are handed, and monitor-select's subtitle family, whose "unset means the label's" fallback is applied *before* resolution because the resolver answers an empty name with the platform sans. So no backend or render component calls the resolver on a family it was given, and none may resolve per draw — the pointer redraws on every cursor move. **`PointerAppearance` carries every settled pointer value, not just the family**: those same three components read the char and the font size out of the configuration they are handed too, so `buildVirtualPointerStyle`'s fallbacks to the documented `●` at 8pt travel on that notification and are substituted at the same place (#1337) — settling them again inside a component would be three copies of a default on the Objective-C boundary, and leaving them unsettled is what made a written `char = ""` draw the default on Linux and nothing on macOS. The Linux and Windows draws each still carry their own empty-char fallback to a `●` literal; both are unreachable from the app now that the Style settles the char, and neither is the place to add a second one. Read one via `overlay.ResolvedStyle(source)`; a `BuildStyle` call anywhere else re-creates the fan-out this replaced, and a missed call site leaves an overlay in the previous theme's colours. **Still outside it**: the mode-indicator, sticky-indicator and virtual-pointer overlays hold their own `ThemeProvider` (handed to them at construction) and resolve their colours at draw time, and the click indicator's style is built in `app/services/action_service.go`. The pointer drawn on a grid surface is inside it: `UpdateGridPointer` meets a position from the caller with the resolved virtual-pointer Style here (#1211), so no mode reads a style to move it.
- **The overlay builds its own render components** (#1209): `Base.BuildComponents` (`manager/components.go`) constructs them from a `ComponentSpec` — configuration, theme provider, logger, window handle, headless verdict — and keeps them; the app hands over the first two and reads nothing back. The built set was returned for the "was this overlay built at all" guards in `app/lifecycle.go`; those went with #1213, because a screen change now hands over a Frame and every draw already answers "never constructed" here. No app-layer type names a render component. The window handle and the headless verdict come from the backend's own `BuildComponents`, which is the only reason that delegate exists: a `Base` cannot see the surface, and a `Base` method cannot dispatch to a backend's override (darwin's `UseVirtualPointerOverlay` propagates screen-share state, so darwin re-applies it after the build). A backend delegate must nil-guard its receiver like every other exported method here. A failed component is logged and left nil; only the virtual pointer fails the build, because that is the one the app's startup phase treated as fatal.
- **An Indicator is driven through the port, never through its render object** (#1208): `ShowIndicator` / `HideIndicator` / `ResizeIndicatorToActiveScreen` take a `ports.Indicator`; `manager.Base` resolves it to a render component and answers "never constructed" itself, so no caller nil-checks one. `HideIndicator` owns clearing as well as hiding — on macOS the component has its own window, on Linux it is a badge painted on the shared surface and hiding it means erasing that rectangle (`linux/manager.go` overrides it for exactly that). The app side is one service per indicator in `app/services/{modeindicator,stickyindicator,virtualpointer}`, all built on `app/services/indicator`.
- **A mode hands over a Frame; this package owns the sequence that realises it** (#1210): `Adapter.ShowFrame` (`adapter.go`) is the only place `ResizeToActiveScreen` → `Show` → `SwitchTo` → draw exists, and `ClearFrame` the only place the leaving half does. `RedrawFrame` draws a frame already on screen and deliberately skips the window sequence — hint labels narrow on every keystroke, and a `Show` per keystroke is a `dispatch_async` of window level, collection behaviour and ordering that ADR 0003 rules out. A `ports.Frame` carries domain values only: converting them to render models and meeting them with the resolved Style happens here and nowhere upstream, and `internal/architecture/overlay_frame_test.go` fails the build if a Frame field is typed from anything but the standard library or `internal/domain/`. Every surface is a frame since #1212, and the window sequence is the one thing a frame varies: `drawsOnSharedWindow` says no only for monitor-select, whose panels are per-display windows on macOS and whose Linux draw shows the spanning window itself — bringing an empty always-on-top window up behind them would put something on screen that nothing draws into. Scroll draws nothing and still says yes, because on Linux the mode and sticky-modifier badges are painted on that surface: a hidden shared window is an invisible indicator, and answering from macOS's one-window-per-indicator model would strand a Linux user in scroll mode with no indicator after a monitor move. Drawing the picker stays an optional capability reached by type assertion (`manager.MonitorSelector`), asserted in `Adapter.drawMonitorSelect` rather than by widening the port; a backend without it reports `CodeNotSupported` and the mode refuses to activate. `ClearFrame` also takes the panels down — they are not on the shared surface, so clearing that surface leaves them on screen — and `monitorSelectDrawn` is the second piece of screen state this package keeps, for the same reason `subgridDrawn` is the first.
- **Each grid surface says what its draw needs, and the updates stay calls** (#1211): a grid draw clears the surface when the frame is coming up or when a subgrid is on it — the backend's incremental path compares grids and cannot diff a subgrid away, and `Adapter.subgridDrawn` is the one piece of screen state this package keeps, because `ShowGridSubgrid` is what put it there. Clearing on every redraw instead would blink the mode and sticky-modifier indicators off the shared Linux surface until the next poll, on every theme change. **An open subgrid is the whole grid surface, not a layer over the cells** (#1491): macOS is what settles that, and `paintSubgridSurface` (`linux/overlay_shared_cgo.go`) is where the evidence for it is written down. Linux says it once — `redrawGrid` is the only answer to what that surface shows and delegates to that function while `currentSubgrid` is set, so the open, a narrowing keystroke and a pointer move all reach the same screen; a second painter answering for itself is what put the parent cells back under the subgrid on the first keystroke after an open. A recursive-grid draw clears on the transition only, because that backend animates from the bounds it last drew: a fresh activation must not zoom out of the region the last one left, and a keystroke must. Everything a keystroke changes in grid mode stays a plain call by ADR 0003 — `UpdateGridMatches`, `SetGridHideUnmatched`, `ShowGridSubgrid`, `UpdateGridPointer` — and none of them builds a frame. **A call widens rather than a keystroke costing two of them** (#1492): `ShowGridSubgrid` carries the pointer the way a recursive-grid frame does, because the keystroke that picks a cell is the keystroke that moves the selection, and where both are painted into one surface saying it twice repaints it twice — arrow keys inside a subgrid included, once per repeat of a held key. That is the hybrid's update half answering the same problem the frame half answers with a Frame, and it is the answer here because a frame on this path is what ADR 0003 rules out. The pairing is free off Linux: `manager.Base.ApplyGridPointer` puts the state onto the render component after the draw, which is a layer update and not a repaint, and a backend that overrides `DrawGridPointer` must not reach it — Go dispatches to `Base`, not to the override, which is why the Linux and Windows managers implement the carrying draw themselves. **The leaving half owns what the update half left**: `ClearFrame` drops the hide-unmatched flag and the pointer, both after the clear so neither paints, and the match prefix needs no reset because a grid coming back up is a transition that clears and redraws in full. A mode resetting those for itself was a mode repainting a grid twice on the way to throwing it away. Recursive grid has no incremental path: its keystroke redraws the whole surface, so it hands over a frame, and that costs one interface boxing per key (measured on #1211: grid narrowing unchanged in time and allocations, recursive grid +1 allocation of 128 B with no measurable time cost). The pointer stand-in a grid mode draws is **not** an Indicator — it belongs to the mode's own drawing, and `manager.Base` resolves the mode to a render component (`DrawGridPointer`/`HideGridPointer`) the way it resolves an indicator. **The whole resolved appearance travels with the position** (#1463): a render component reads the char and the family out of the configuration `ConfigureComponents` handed it and needs only the size and the fill, but off darwin no render component owns a surface at all, so a backend painting the glyph itself has nowhere else to read them — which is why grid mode's pointer was a Linux no-op while recursive grid's, riding the frame, was not. The Linux and Windows managers therefore override both, keep the state on the backend and paint it in whichever repaint of the grid surface comes next — the cells or the subgrid on them — while recursive grid is delegated back to `Base`, because its pointer is already in the frame every keystroke hands over and a second path would repaint a grid that mode never drew.
- **The hint search input's geometry is resolved here too** (#1210): `SearchInputLayout` travels with the Style, so a config reload moves the box and a draw does no configuration lookup; `searchInputFrame` places it against the screen the caller names and clamps it on. `HintSearchBounds` exists because the platform IME field has to sit over the same rectangle — asking beats deriving it a second time in the mode layer. Every anchor `config.SearchInputPositions()` declares has a branch there and an anchor outside it is refused, not approximated (#1329): `DrawHintSearch` warns and returns `CodeNotSupported` before drawing — the degradation `ports.OverlayPort` already documents for a search input that does not appear — and `HintSearchBounds`, which answers a rectangle and cannot report, answers the empty one, because the box the IME field would sit over was never drawn. The empty string is refused with the rest rather than settled to the default the way `hints.ui.placement` is: the validator refuses an unset position, so the only Style carrying one is a Style nothing resolved. **What each backend then does with that rectangle differs, and on Linux the badge is not a window** (#1458): it is painted onto the shared Cairo surface over the labels, like an indicator badge and with no clear of its own, so the manager remembers the rectangle it covered and *hiding* it repaints the hints rather than erasing that rectangle — erasing it would take a bite out of the labels, which is what the confirm path leaves on screen. A hints draw clears the whole surface, so it forgets that rectangle too, and the hide that follows a canceled search has nothing left to take down. The label itself is `badge.SearchLabel`, untagged and tested there: what the box says is not a per-backend decision. macOS and Windows keep their own, and only Linux reads that one today.
- **A hint placement no backend branch names is refused, not approximated** (#1331, #1333, #1303): `hints.ui.placement` is read in exactly one function per backend — `resolveHintBadgeOffset` (`linux/manager.go`), `resolveHintBadgeOffset` (`windows/manager.go`) and `hintPlacementValue` (`render/hints/overlay_darwin.go`) — every value `config.HintPlacements()` declares has a branch there, and anything else is warned about and reported as `CodeNotSupported` before a label is painted. All three now draw all three placements, so a placement added to the vocabulary without a branch is refused loudly everywhere rather than silently drawn somewhere (`docs/CROSS_PLATFORM.md` owns that status). The drawing code below each takes the resolved offset or native constant rather than the configured string, so a placement with no branch cannot reach it; on macOS that means the full redraw and the incremental structural update are both fed one value resolved once per draw, and on Windows the redraws that replay the last hints (around the search input) replay the offset that draw was accepted with rather than re-resolving in a call with nowhere to report. **The geometry the offset selects has one implementation**: `badge.PlaceHint` / `badge.HintRadius` (`render/badge/hint.go`, untagged and tested there so it runs on every CI leg) answer the badge rect and the connector arrow for Linux and Windows alike; only what each surface can paint differs — Cairo merges badge and arrow into one outline (`hintTailEdge` stays in `linux/manager.go` because those values are the C renderer's), while the Win32 surface has no path primitive and composites the arrow as a triangle over a border-coloured one. The empty string is the exception all three make — it settles to `config.HintPlacementDefault`, because a Style can reach an overlay before a configuration settles it and refusing it would draw no hints at all, while `hints.search_input_ui.position` refuses an unset value for the opposite reason above. The refusal travels to the mode handler unwrapped (`darwin/manager.go` passes `CodeNotSupported` through rather than wrapping it as `CodeOverlayFailed`), which degrades on it the way it does for a backend that reports no hint surface: hints mode stays up and the labels are not drawn, rather than every label being put somewhere the user did not choose. It refuses without clearing — a draw that was refused painted nothing, so whatever the last accepted draw left is still on screen and still describes it, which is also what keeps the incremental path's cached state truthful. An empty hint set still clears, placement or not: taking labels off the screen does not need one.
- **`Destroy` is final, and the shutdown order is not the only thing that says so** (#1515): `Adapter.destroyed` is set before the backend is released, and every method the port declares no-ops after it. The drawing ones report success rather than an error — a mode exiting into a teardown is a race the shutdown already won, not a failure a user needs told about, and their callers log whatever comes back — while `IsVisible` and `HintSearchBounds` answer "nothing on screen" and `Health` reports `CodeNotSupported`. It is an `atomic.Bool` and not the mutex `eventtap.Adapter` guards the same state with (#1514), because this adapter holds no lock of its own and must not grow one: a draw already runs `h.mu` → `renderMu`, and a lock between them would sit on the edge every keystroke's draw crosses. The release itself runs outside any hold for that same reason, and a second caller waits on the first one's teardown so the method keeps its postcondition. `App.Cleanup` still tears the **event tap** down first, because the tap's teardown drains its key dispatcher and that drain delivers a queued key into the mode handler, which draws: the ordering is what lets the drain finish onto a live surface instead of onto a guard, and the guard is what holds when a later caller gets the ordering wrong. `TestAdapterDestroy_StopsEveryPortCallFromReachingTheBackend` (`adapter_destroyed_test.go`) pins the guard and `TestSimulation_ShutdownDrainsTheEventTapBeforeReleasingTheOverlay` (`internal/app`) the ordering. **One port call is published on a goroutine of its own, and neither the flag nor the ordering can close it**: `SetHiddenInScreenShare` arrives from `state.AppState`, which notifies each screen-share subscriber with `go callback(...)`, so a callback can be past the `destroyed` check while the release runs — and unsubscribing does not reach a goroutine already launched, which is why `App.Cleanup` moving that unsubscribe above the teardown narrows the window rather than closing it. It is closed where the state lives: darwin's `shareMu`, already dedicated to that flag so it never contends with `SwitchTo`/`Subscribe`, is taken across `Manager.Destroy` too, and nothing under it blocks on the main queue (every native call it makes is a `dispatch_async`), so a teardown running on the main thread cannot wait on a holder waiting on that thread. `TestManager_Destroy_DoesNotOverlapSetSharingType` (`darwin/manager_screenshare_test.go`, under `-race`) pins it. Linux and Windows answer `SetSharingType` with a no-op and have no such pair. **What that ordering costs is that the overlay is live during the drain**, and on darwin the indicator draws are the one thing on it that is not `dispatch_async`: `DrawModeIndicator` and `DrawStickyModifiersIndicator` reach `NeruPositionAndSizeOverlayToFitHint`, an unconditional `dispatch_sync` onto a main queue nothing is servicing by then (`App.Cleanup` runs on the main thread after the Cocoa loop has stopped). It is unreachable today — `Cleanup` exits the mode before the drain, so indicator polling is already joined, and a drained hotkey's sequence runs on a goroutine of its own (`modes/key_dispatch.go`) — but a change that lets a drained key exit a mode **inline** while polling is live parks the drain on `stopIndicatorPolling`'s join under `h.mu`, which is the #1514 hang one layer over.
- **No app package imports this one** (#1213): the shared-infrastructure allowlist entry in `layering_test.go` is gone, so `internal/architecture` fails the build if one does again. Everything the app says to the overlay it says through `ports.OverlayPort` — frames and updates, plus the four calls that used to reach past it: `ApplyConfig` and `RefreshStyles` (the one notification a config reload or a theme change owes the resolver), `SetHiddenInScreenShare`, and `Destroy`. `overlay.Init` is named by the composition root alone (`app/wiring.go`), and the `OverlayManager` alias it is declared beside travels no further than the `App` field that holds the backend between the phase that builds it and the phase that builds the adapter over it (`app/startup_phases.go`, `app/app.go`); `app.WithOverlayPort` replaces it wholesale, and a session that brings its own port builds no backend at all. The Linux keyboard grab is `SetKeyboardCaptureEnabled` on the port, answered here by asserting `manager.KeyboardCaptureController` on the backend — a plain method rather than a port-level capability, because asking is always safe and what confines the behaviour to Linux is the caller's gate on the **event tap**, not the overlay. The package singleton `Get()` is no longer reached from `app/modes`; its only remaining caller is the Linux event tap. `render/*` owns style and drawing only: the per-mode `Context` types that lived in `render/{hints,grid,recursivegrid}` were mode state, not render models, and moved to `internal/app/components/`. Optional backend capabilities are still reached by type assertion, not interface widening.
- **`manager.Interface` is wide on purpose, and internal.** It is the contract between this adapter and its backends, and narrowing it is not what the port work was for. No package outside this one implements it and none but the composition root names it (`app/wiring.go` aliases it to build the adapter over), the no-op manager that used to stand in for a display is gone from the shipped binary (#1213), and the headless base the adapter's own tests build fakes on lives in `headless_manager_test.go`.
