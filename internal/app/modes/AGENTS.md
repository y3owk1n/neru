# Mode handler — locking contract (deadlock hazard)

`modes.Handler` is split for compiler-enforced locking: the outer `Handler` owns `mu` and the exported entry points (`HandleKeyPress`, `ActivateMode`, `ExitMode`, …), each of which locks and delegates into the embedded `handlerState`, which carries all fields and lock-held methods and has no mutex. Modes are built on `*handlerState`, so calling a locking entry point from locked context is a compile error.

- Deferred callbacks (timers, goroutines) reach the lock via `handlerState.outer` — **never call it synchronously**; from a method running under `h.mu` it self-deadlocks.
- Lock order: `moveMonitorMu` → `h.mu` → `StyleResolver.mu`, never the reverse. Reading a Style under `h.mu` is safe because the resolver's read lock is taken and released by the reader and the resolver never calls back into the handler; handler context must never reach the resolver's `applyMu`, which is held across pushes into the render components. Since #1212 *every* one of those reads happens inside the overlay adapter — the handler holds no style source at all — so the edge is entirely `h.mu` → adapter → `StyleResolver.mu`, reached through a draw rather than by a mode asking for a Style. Any new mutex needs a stated position in that order. One adapter-side mutex earns its own clause because it is reached from locked context and can be held for minutes: `platform/linux`'s `screenCastState.mu` (KDE screen capture) sits at `h.mu` → `screenCastState.mu`. The one path that reaches it under `h.mu` — a capture during hints activation — takes it with **TryLock** and fails loudly rather than waiting, because `RequestScreenCapturePermission` holds it for as long as a user takes to answer KDE's screen-sharing dialog; that one is contractually off the lock (`ports/system.go`). `CheckScreenCapturePermission` also runs under `h.mu` and takes no lock at all, reading an atomic instead, because the port requires it to answer true the instant a consent is granted and a busy mutex would have it answer false. Nothing holding that mutex reaches the handler, so the edge is one-way.
- Don't hold `h.mu` across blocking calls (IPC, exec, channel sends, overlay draws, modal dialogs) or adapter calls that can synchronously call back into the handler. Overlay draws may block by contract (`internal/adapter/overlay/AGENTS.md`). One exec is deliberate: the pre-activation cursor sync (`syncCursorPosition`, `validation.go`) may shell out to a compositor CLI on Wayland, under the same one-shot-with-a-read-deadline carve-out the accessibility bullet below draws — it is bounded by `cursorSyncTimeout`, the exec kills on expiry with a `WaitDelay` pipe guard (`compositorcli.QueryContext`), and it replaced a layer-shell discovery wait of the same shape; a new exec under the lock needs that whole argument, not just a timeout. Three kinds of call still reach the overlay under the lock and all are deliberate. **The hints surface**: since #1210 it goes through the handler's overlay surface, but it still draws under `h.mu`, because the hint manager's update callback fires from `SetHints`/`Reset`/`HandleInput`, which already hold it — that is `drawHints` (`hintdraw.go`), and with it `HintsMode.RefreshForThemeChange`, `drawHintSearchInput`, `hideHintSearchInput` and `hintSearchBounds`, which reach the same surface from the same locked context. The first draw of an activation is a *transition*, so `ResizeToActiveScreen` → `Show` → `SwitchTo` run under `h.mu` too (`overlay/adapter.go`, `ShowFrame`) — which is what makes "nothing holding `renderMu` may take `h.mu`" and "macOS `Show` stays `dispatch_async`" load-bearing rather than incidental. `hintSearchBounds` and the grid surfaces both reach `StyleResolver.mu` through the adapter; that is the documented order, not an exception to it. **The grid surfaces**: since #1211 grid and recursive grid go through that same surface, and like hints they draw under `h.mu` — activation hands over a Frame from locked context (`grid.go`, `recursive_grid.go`), and so do the per-keystroke updates, which run from the grid manager's update callback fired by `HandleInput` under the lock (`frames.go`). An activation runs the `ShowFrame` window sequence, and since #1213 so does a **screen change**: `GridMode.RefreshForScreenChange` hands over a Frame, `RecursiveGridMode.RefreshForScreenChange` does too, and `HintsMode.RefreshForScreenChange` clears `hintsFrameOnScreen` so the `SetHints` callback shows rather than redraws — the display moved under the overlay, so resizing and re-showing is part of realizing the frame and no longer open-coded in `app/lifecycle.go`. A keystroke never runs it, including the one that leaves a subgrid — that is a `RedrawFrame`, and erasing the subgrid is the adapter's business. The screen-change callers are goroutines, never the main queue, and the one `dispatch_sync` inside `ShowFrame` (hiding the monitor-select panels) is gated on the picker being drawn, which no screen-change refresh can be. Nothing there computes a plan and draws after release, because there is nothing to release to: the whole activation is one locked entry point. Since #1212 the same is true of the last two surfaces: monitor-select hands over a Frame on activation, on every keystroke and on a theme change, and scroll hands over one on activation — all from locked context, and neither brings the shared window up. **Mode teardown**: `stopIndicatorPolling` hides each indicator and `performCommonCleanup` clears the frame, both of which take the Linux manager's `renderMu`. Since #1492 that clear is the *whole* of what grid mode's teardown says to the overlay: `cleanupGridMode` no longer resets the hide-unmatched flag, the match prefix or the pointer, because doing so repainted the grid — twice — on the way to throwing it away, and `ClearFrame` drops all three after the surface is already down. Anything a mode wants the overlay to forget on the way out belongs there for the same reason. A monitor move clears the frame under `h.mu` too (`clearFrameForMonitorMove`), from `MoveMonitor`'s `moveMonitorMu`, which is the documented order and the reason that lock sits above `h.mu`. Putting the mode back on the other side is one hold of its own and since ADR 0004 it covers the whole refresh, hints' accessibility walk included — the same walk activation already holds the lock across. What stays outside every hold is the animated cursor warp between the two: `moveCursorToMonitor` is clear → warp → redraw, and moving the lock up must never be allowed to swallow the middle step. Note what that clear can reach on macOS: with monitor-select panels on screen it makes a **synchronous** hop to the main queue (`NeruHideMonitorSelectPanels` is a `dispatch_sync`), so `h.mu` is held across a main-thread round trip. That is safe only while nothing running on the main queue takes `h.mu` — the event tap only enqueues onto its dispatcher, the hotkey callback starts a goroutine, the app watcher's activation callback writes an atomic cell (`PublishFocusedApp`, `keymap.go`) and starts a goroutine for the one thing that cannot wait to be read from it (the bullet below), which is why that one is lock-free by contract rather than by accident, and the hint-search text field notifies on the main thread and synchronously — `notifyQueryChanged` fires from `didChangeText`, `insertText:` and `setMarkedText:`, and `keyDown:` calls confirm and cancel inline (`internal/adapter/platform/darwin/textinput_darwin.m`) — reaching the three callbacks `startHintSearch` registers (`handler_actions.go`), every one of which takes `h.outer.mu`, and safe only because each exported bridge hands the callback to a goroutine before invoking it (`internal/adapter/textinput/textinput_darwin.go`), which is the same property the hotkey callback and the app watcher rest on. Any new main-queue callback that reaches the handler breaks it. That field is the same hazard's other direction as well: `startHintSearch` runs under `h.mu` and both `StopHintSearchSession` and `StartHintSearchSession` put their work on the main queue and wait for it there (`NeruStopHintSearchTextInput` and `NeruStartHintSearchTextInput` run the block inline when they are already on the main thread and `dispatch_sync` when they are not, which from the handler is always), so the monitor-select clear above is not the only place `h.mu` is held across a main-thread round trip — it is the same *kind* of round trip and it is safe for the same reason. Those two are also where the goroutine hop stops being stylistic: `startOnMainThread` (reusing a live panel) and `stopOnMainThread` both call `notifyQueryChanged` themselves, so the query callback fires *inside* that round trip, with the handler's goroutine parked holding `h.mu` — invoke it inline there and the main thread waits on a lock its own caller is holding. The adapter's own order is what leaves the hop room to work: `StartHintSearchSession` and `StopHintSearchSession` write `t.callbacks` and release `t.mu` before entering C, so the bridge's callback lookup on the main thread cannot block on the caller either. The `renderMu` direction is safe because nothing holding `renderMu` ever takes `h.mu`: the overlay never calls into the app, and the handler is not an overlay subscriber. Lock order there is `h.mu` → `renderMu`, never the reverse. The indicator hide cannot move off the lock — it has to happen after the polling goroutine is joined, or a late tick puts the indicator back on screen.
- **The compiler refuses the four overlay calls that invert the lock order.** `ApplyConfig`, `RefreshStyles`, `SetHiddenInScreenShare` and `Destroy` belong to the app's config, theme and shutdown paths, which run unlocked: from locked context `RefreshStyles` gives `h.mu` → `StyleResolver.applyMu` → the render components, and `Destroy` is a `dispatch_sync` to the main queue under `h.mu`, both inversions of the lock order above. Until #1213 the resolver lived on `App` and the compiler enforced this; since #1423 it enforces it again, because the handler no longer holds `ports.OverlayPort`. It holds `overlaySurface` (`overlay.go`) — the thirteen of the port's twenty-seven methods this package calls, declared at the consumer the way `internal/app/keybinding/hotkey.go` documents — and the other fourteen do not compile here. That is the whole enforcement and no test adds to it: the port mocks are counter no-ops that can neither block nor fail, so such a call would deadlock only against a real display server, which is exactly why the rule is a type and not a sentence (ADR 0011). Two things would lose it: widening `overlaySurface`, and asserting the field back to the full port — the package does reach for that idiom elsewhere (`eventtap.go`, `validation.go`, both on other fields) and must never point it at this one, because the value behind the field is a whole `ports.OverlayPort` and the assertion would succeed. So the type's doc comment names each excluded group and points back here for the inversions above.
- The handler holds exactly one overlay reference, `overlayPort`, typed as `overlaySurface`. The Linux keyboard grab that used to reach the overlay package's singleton is `overlayPort.SetKeyboardCaptureEnabled`, gated as before on the **event tap** reporting overlay keyboard passthrough (#1213); no file here imports `internal/adapter/overlay`, and `internal/architecture/layering_test.go` fails if one does. The indicator draws are not on that surface at all — an indicator's life belongs to the service that owns it, each holding its own `ports.OverlayPort`, and the hides in `stopIndicatorPolling` still run under `h.mu` through those services as the bullet above describes — so the handler's share of *that surface* is `Flush`, which commits a tick's draws in one go.
- **Every accessibility call that queries the platform tree under `h.mu` carries a deadline**, because `h.mu` serializes key handling and an unbounded query there lets a hung application stop the keyboard. The element walk is the one that matters and it gets `HintTimeout` on all three paths that run it: activation (`hints.go`), monitor move (`monitor.go`) and screen change (`handler_refresh.go`, since #1243). `validation.go` bounds its exclusion check with `ValidationTimeout`. A new call site that walks a tree needs its bound in the same change. What is *not* covered by this rule: calls that post a synthesized event rather than query a tree (`ReleaseHeldButtons` in `cleanup.go`, `PerformActionAtPoint` in `mode_handlers.go`) — they reach `checkContext` and then a local post, so a deadline buys them nothing and their absence is not a violation. **A Go deadline is only worth adding where the callee reads it.** The darwin element walk polls the context as it descends, so `HintTimeout` genuinely cuts it short. The focused-application query does not: `FocusedApplication` (`internal/adapter/accessibility/native/client.go`) takes `_ context.Context` and makes a synchronous native call, so wrapping its caller in a timeout is inert — the deadline is created microseconds before its only check and cannot expire in between. Bounding that one means a bridge-level messaging timeout, not a context. That unboundable query is why the line this rule draws is **one-shot versus keystroke, not accessibility versus not**: a one-shot the user is waiting on may block under the lock while it carries a bound the callee reads — a walk that stalls is the hints they asked for being slow — but a keystroke may not block at all, because someone typing a hint label is waiting on nothing and the same stall is the daemon frozen, mode exit included. So since ADR 0005 no keystroke asks it: the app watcher publishes the focused app into a lock-free cell and the keymap is settled from it (`keymap.go`). `resolveFocusedApp` still asks while nothing has published — always on Windows and on a Linux session with no focus source, and on macOS until the watcher first fires — but only while settling for a mode being entered or a configuration being replaced, both of which are one-shots. A keystroke can only re-settle from something that *was* published, so it never reaches the ask. Putting an unbounded call back on the keystroke path is a violation whether or not it carries a deadline.
- **State a focus change moves is settled on a read; the event tap's copy of it is pushed.** ADR 0005 has the app watcher publish the focused app into a lock-free cell and the keymap settle from it on the next read, because a keystroke *is* that read. The event tap's passthrough lists are the exception, and the reason is that they decide whether there will be a next read at all: an unblacklisted chord goes to the focused application instead of to Neru, so waiting for a keystroke means waiting for the keystroke that already went elsewhere. So they are pushed — `RefreshPassthroughForFocusedAppChange` (`passthrough.go`), a locked entry point started **on a goroutine** by `handleAppActivation` (`app/lifecycle.go`), never called inline from the watcher callback, which on macOS is the main queue. What the goroutine buys is only that the handler is reached off the main queue: it still queues behind whatever holds `h.mu`, so the guarantee is "as soon as the handler is free", not "before the next key". Anything else a focus change has to move goes the same way — settled on a read, or pushed through a goroutine — and never straight from the callback. The order those pushes take is `h.mu` → the event tap adapter's `mu` (`adapter/eventtap/adapter.go`), which every handler caller of `syncModifierPassthrough` has always used; the rule that comes with it is that **nothing holding the adapter's `mu` may wait on anything that takes `h.mu`**. `Adapter.Destroy` breaks it today — it holds that `mu` across `dispatchWg.Wait()`, and the dispatcher it waits for drains keys into `HandleKeyPress` — so a shutdown racing any pusher can deadlock. That is older than this rule and not fixed here; do not add a second violation.
- **No method releases a lock it did not take** — every lock is released, via `defer`, by the method that took it; never unlock mid-method to make a blocking call safe. Instead compute a plan under the lock and have the lock-taking method execute it after release (`planIndicatorTick`/`drawIndicators` in `indicator_polling.go`), or hand the blocking call to a goroutine that re-enters through the outer locked surface guarded by the mode-session token (`requestScreenCapturePermissionAndResume` in `hints.go`).
- **Everything the handler holds is reconfigured through `Handler.UpdateConfig`**, never from the app's reconfigure path. The mode components (`h.grid`, `h.scroll`) carry domain state derived from configuration, and the grid manager — the one that matters — has no lock of its own: the handler assigns it on activation and reads it on every keystroke, both under `h.mu`. So `updateComponentConfigs` lives here (`handler.go`) and runs inside the same hold; a reload calling `GridComponent.UpdateConfig` from `app/config.go` was a plain data race on live mode state (#1277), the same shape #459 had for the mode indicator. `App.reconfigureRuntimeFromConfig` reaches the handler only through `a.modes.UpdateConfig`, and a new piece of handler-held state derived from config is reconfigured there or not at all. Its `-race` regression is the one test on this list that does not live here: driving a reload against an activation needs the whole app, so it is `TestSimulation_ConfigReloadRacingGridActivation` in `internal/app` and `go test -race ./internal/app/modes/` alone will not run it.
- **Mode-lifecycle dispatch takes `h.mu` once**, and the whole of it — reading the active mode, selecting the implementation, calling the method — happens inside that one hold. A mode cannot change between being chosen and being used, so **an implementation must not re-check the active mode**; a re-check reads reasonable in isolation and is exactly what was deleted, so add one only with a caller that genuinely selects unlocked. `refreshActiveModeForMonitorMove` (`monitor.go`) is the pattern, `RefreshActiveModeForThemeChange` and `RefreshActiveModeForScreenChange` (`handler_refresh.go`) follow it, and ADR 0004 (`docs/adr/0004-mode-lifecycle-dispatch-under-one-lock-hold.md`) is why. There is no exception left: the screen-change dispatch was the last caller that snapshotted the mode unlocked, and the three re-checks that guarded that window went with it. The screen-change dispatch answers its caller with whether the overlay still needs a resize of its own; the app layer performs that resize but no longer decides whose overlay it is, and idle is answered inside the same hold, because resizing is what brings the overlay up and a display change with nothing open has to leave it hidden.

The `Mode` interface is `Activate(modecmd.Activation)`, `HandleKey(string)`, `Exit()`, `ModeType()`, `RefreshForMonitorMove(context.Context, image.Rectangle)`. Each mode is its own type: embed `baseMode` (`base.go`), which supplies the handler reference and answers `ModeType`, then write the other four as methods on that type — there is no shared fallback, so what a mode does on each of them is answered by reading the mode. Add a `var _ Mode = (*XMode)(nil)` assertion and register in `newModes` (`handler.go`). `Handler.ActivateMode` is the only activation entry point. Monitor-move refresh is core rather than an optional extension because all five modes participate — even scroll, which draws nothing but still has to switch the overlay back to the mode its indicators name — and because a mode that quietly failed to implement it would leave an overlay stranded on the display the user left.

Behavior only *some* modes have is an **optional extension**, never an arm of a switch over `domain.Mode`. An extension is a narrow unexported interface in `extensions.go`, named for what it does, reached from a call site with a comma-ok type assertion through `activeModeExtension[T]` — the idiom the port layer already uses for `ports.CursorSettler` and `ports.RelativeCursorMover`. Do not call these *capabilities*: that word names the platform capability model and the capability matrix (`docs/CROSS_PLATFORM.md`), and the collision is why this framing exists. `TestModeHandlerHasNoSwitchOverDomainMode` (`internal/architecture/mode_extension_switch_test.go`) fails when a switch in this package matches on a `domain.Mode` constant, because `exhaustive` covers the wrong half of that rule: it fires on an *incomplete* switch, and the complete one a careful contributor writes — every constant listed, the modes that do not participate given an empty arm — lints clean. Its exemption list carries a reason per entry, and `TestKnownModeSwitchExemptionsAreStillReal` fails on an entry that has stopped naming a switch, so the list can only shrink.

- Each implementer states what it carries with a `var _ <extension> = (*XMode)(nil)` assertion beside its `var _ Mode` one. Without it, a signature drift silently downgrades the mode to the not-implemented path everywhere instead of failing the build.
- Absence semantics depend on what the axis is. A **getter** is reached through `activeModeExtension` and its absence yields the zero value with no log — the same nothing the empty switch arm said, and what a caller of a two-result getter already handles. An **effect** is reached through `activeModeEffect` instead, which logs at debug naming the mode and the axis, because an absent effect is a key the user pressed that did nothing and "backspace did nothing in this mode" has to be answerable from a log rather than by reading the switch. Input editing, theme-change refresh and screen-change refresh are the effect axes today; every other axis is a getter. The axis names in that log are the `extensionName` constants in `extensions.go` — the same ones the matrix rows use, so the log and the matrix cannot drift apart.
- Carrying an axis and doing nothing on one of its methods is a different statement from not carrying it, and stays silent: `HintsMode.ResetInput` is empty because hints has no input to clear, and hints still carries input editing because it does answer backspace. Say which it is in the method's doc comment.
- `TestModeExtensionMatrix` (`extensions_test.go`) is what replaces the exhaustiveness `exhaustive` gives a switch over `domain.Mode`. It iterates the handler's live mode map, so a mode registered in `newModes` shows up without anyone remembering, and fails until its row states every axis. A new extension is added to `allExtensions` there once and is then asserted for every mode. **If that test stops having teeth, the extension model is unsafe — fix it before adding another axis.**

Concurrency-sensitive changes need a test that fails under `-race`: `go test -race ./internal/app/modes/`. Run the `deadlock-reviewer` agent on the diff before opening a PR.
