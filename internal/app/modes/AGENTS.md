# Mode handler — locking contract (deadlock hazard)

`modes.Handler` is split for compiler-enforced locking: the outer `Handler` owns `mu` and the exported entry points (`HandleKeyPress`, `ActivateMode`, `ExitMode`, …), each of which locks and delegates into the embedded `handlerState`, which carries all fields and lock-held methods and has no mutex. Modes are built on `*handlerState`, so calling a locking entry point from locked context is a compile error.

- Deferred callbacks (timers, goroutines) reach the lock via `handlerState.outer` — **never call it synchronously**; from a method running under `h.mu` it self-deadlocks.
- Lock order: `moveMonitorMu` → `h.mu` → `StyleResolver.mu`, never the reverse. Reading a Style under `h.mu` is safe because the resolver's read lock is taken and released by the reader and the resolver never calls back into the handler; handler context must never reach the resolver's `applyMu`, which is held across pushes into the render components. Since #1212 *every* one of those reads happens inside the overlay adapter — the handler holds no style source at all — so the edge is entirely `h.mu` → adapter → `StyleResolver.mu`, reached through a draw rather than by a mode asking for a Style. Any new mutex needs a stated position in that order.
- Don't hold `h.mu` across blocking calls (IPC, exec, channel sends, overlay draws, modal dialogs) or adapter calls that can synchronously call back into the handler. Overlay draws may block by contract (`internal/adapter/overlay/AGENTS.md`). Three kinds of call still reach the overlay under the lock and all are deliberate. **The hints surface**: since #1210 it goes through `ports.OverlayPort`, but it still draws under `h.mu`, because the hint manager's update callback fires from `SetHints`/`Reset`/`HandleInput`, which already hold it — that is `drawHints` (`hintdraw.go`), and with it `HintsMode.RefreshForThemeChange`, `drawHintSearchInput`, `hideHintSearchInput` and `hintSearchBounds`, which reach the same surface from the same locked context. The first draw of an activation is a *transition*, so `ResizeToActiveScreen` → `Show` → `SwitchTo` run under `h.mu` too (`overlay/adapter.go`, `ShowFrame`) — which is what makes "nothing holding `renderMu` may take `h.mu`" and "macOS `Show` stays `dispatch_async`" load-bearing rather than incidental. `hintSearchBounds` and the grid surfaces both reach `StyleResolver.mu` through the adapter; that is the documented order, not an exception to it. **The grid surfaces**: since #1211 grid and recursive grid go through the same port, and like hints they draw under `h.mu` — activation hands over a Frame from locked context (`grid.go`, `recursive_grid.go`), and so do the per-keystroke updates, which run from the grid manager's update callback fired by `HandleInput` under the lock (`frames.go`). An activation runs the `ShowFrame` window sequence, and since #1213 so does a **screen change**: `RefreshGridForScreenChange` hands over a Frame, `RefreshRecursiveGridForScreenChange` does too, and `RefreshHintsForScreenChange` clears `hintsFrameOnScreen` so the `SetHints` callback shows rather than redraws — the display moved under the overlay, so resizing and re-showing is part of realizing the frame and no longer open-coded in `app/lifecycle.go`. A keystroke never runs it, including the one that leaves a subgrid — that is a `RedrawFrame`, and erasing the subgrid is the adapter's business. The screen-change callers are goroutines, never the main queue, and the one `dispatch_sync` inside `ShowFrame` (hiding the monitor-select panels) is gated on the picker being drawn, which no screen-change refresh can be. Nothing there computes a plan and draws after release, because there is nothing to release to: the whole activation is one locked entry point. Since #1212 the same is true of the last two surfaces: monitor-select hands over a Frame on activation, on every keystroke and on a theme change, and scroll hands over one on activation — all from locked context, and neither brings the shared window up. **Mode teardown**: `stopIndicatorPolling` hides each indicator and `performCommonCleanup` clears the frame, both of which take the Linux manager's `renderMu`. A monitor move clears the frame under `h.mu` too (`clearFrameForMonitorMove`), from `MoveMonitor`'s `moveMonitorMu`, which is the documented order and the reason that lock sits above `h.mu`. Putting the mode back on the other side is one hold of its own and since ADR 0004 it covers the whole refresh, hints' accessibility walk included — the same walk activation already holds the lock across. What stays outside every hold is the animated cursor warp between the two: `moveCursorToMonitor` is clear → warp → redraw, and moving the lock up must never be allowed to swallow the middle step. Note what that clear can reach on macOS: with monitor-select panels on screen it makes a **synchronous** hop to the main queue (`NeruHideMonitorSelectPanels` is a `dispatch_sync`), so `h.mu` is held across a main-thread round trip. That is safe only while nothing running on the main queue takes `h.mu` — the event tap only enqueues onto its dispatcher and the hotkey callback starts a goroutine — and any new main-queue callback that reaches the handler breaks it. That direction is safe because nothing holding `renderMu` ever takes `h.mu`: the overlay never calls into the app, and the handler is not an overlay subscriber. Lock order there is `h.mu` → `renderMu`, never the reverse. The indicator hide cannot move off the lock — it has to happen after the polling goroutine is joined, or a late tick puts the indicator back on screen.
- `ports.OverlayPort` carries four calls the handler must **never** make: `ApplyConfig`, `RefreshStyles`, `Destroy` and `SetHiddenInScreenShare`. They belong to the app's config, theme and shutdown paths, which run unlocked. Until #1213 the resolver lived on `App` and the compiler enforced this; now `RefreshStyles` from locked context would give `h.mu` → `StyleResolver.applyMu` → the render components, and `Destroy` is a `dispatch_sync` to the main queue under `h.mu`. Both are the inversions the lock order above forbids.
- The handler holds exactly one overlay reference, `overlayPort`. The Linux keyboard grab that used to reach the overlay package's singleton is `overlayPort.SetKeyboardCaptureEnabled`, gated as before on the **event tap** reporting overlay keyboard passthrough (#1213); no file here imports `internal/adapter/overlay`, and `internal/architecture/layering_test.go` fails if one does.
- **No method releases a lock it did not take** — every lock is released, via `defer`, by the method that took it; never unlock mid-method to make a blocking call safe. Instead compute a plan under the lock and have the lock-taking method execute it after release (`planIndicatorTick`/`drawIndicators` in `indicator_polling.go`), or hand the blocking call to a goroutine that re-enters through the outer locked surface guarded by the mode-session token (`requestScreenCapturePermissionAndResume` in `hints.go`).
- **Mode-lifecycle dispatch takes `h.mu` once**, and the whole of it — reading the active mode, selecting the implementation, calling the method — happens inside that one hold. A mode cannot change between being chosen and being used, so **an implementation must not re-check the active mode**; a re-check reads reasonable in isolation and is exactly what was deleted, so add one only with a caller that genuinely selects unlocked. `refreshActiveModeForMonitorMove` (`monitor.go`) is the pattern, `RefreshActiveModeForThemeChange` (`handler_refresh.go`) follows it, and ADR 0004 (`docs/adr/0004-mode-lifecycle-dispatch-under-one-lock-hold.md`) is why. The three screen-change refreshers are the exception that proves it: they are still `*Handler` methods selected by a goroutine in `app/lifecycle.go` that snapshots the mode *without* the lock, so their guards close a real window and stay until the dispatch that selects them moves under one hold too.

The `Mode` interface is `Activate(modecmd.Activation)`, `HandleKey(string)`, `Exit()`, `ModeType()`, `RefreshForMonitorMove(context.Context, image.Rectangle)`. Each mode is its own type: embed `baseMode` (`base.go`), which supplies the handler reference and answers `ModeType`, then write the other four as methods on that type — there is no shared fallback, so what a mode does on each of them is answered by reading the mode. Add a `var _ Mode = (*XMode)(nil)` assertion and register in `newModes` (`handler.go`). `Handler.ActivateMode` is the only activation entry point. Monitor-move refresh is core rather than an optional extension because all five modes participate — even scroll, which draws nothing but still has to switch the overlay back to the mode its indicators name — and because a mode that quietly failed to implement it would leave an overlay stranded on the display the user left.

Behavior only *some* modes have is an **optional extension**, never an arm of a switch over `domain.Mode`. An extension is a narrow unexported interface in `extensions.go`, named for what it does, reached from a call site with a comma-ok type assertion through `activeModeExtension[T]` — the idiom the port layer already uses for `ports.CursorSettler` and `ports.RelativeCursorMover`. Do not call these *capabilities*: that word names the platform capability model and the capability matrix (`docs/CROSS_PLATFORM.md`), and the collision is why this framing exists.

- Each implementer states what it carries with a `var _ <extension> = (*XMode)(nil)` assertion beside its `var _ Mode` one. Without it, a signature drift silently downgrades the mode to the not-implemented path everywhere instead of failing the build.
- Absence semantics depend on what the axis is. A **getter** is reached through `activeModeExtension` and its absence yields the zero value with no log — the same nothing the empty switch arm said, and what a caller of a two-result getter already handles. An **effect** is reached through `activeModeEffect` instead, which logs at debug naming the mode and the axis, because an absent effect is a key the user pressed that did nothing and "backspace did nothing in this mode" has to be answerable from a log rather than by reading the switch. Input editing and theme-change refresh are the effect axes today; every other axis is a getter. The axis names in that log are the `extensionName` constants in `extensions.go` — the same ones the matrix rows use, so the log and the matrix cannot drift apart.
- Carrying an axis and doing nothing on one of its methods is a different statement from not carrying it, and stays silent: `HintsMode.ResetInput` is empty because hints has no input to clear, and hints still carries input editing because it does answer backspace. Say which it is in the method's doc comment.
- `TestModeExtensionMatrix` (`extensions_test.go`) is what replaces the exhaustiveness `exhaustive` gives a switch over `domain.Mode`. It iterates the handler's live mode map, so a mode registered in `newModes` shows up without anyone remembering, and fails until its row states every axis. A new extension is added to `allExtensions` there once and is then asserted for every mode. **If that test stops having teeth, the extension model is unsafe — fix it before adding another axis.**

Concurrency-sensitive changes need a test that fails under `-race`: `go test -race ./internal/app/modes/`. Run the `deadlock-reviewer` agent on the diff before opening a PR.
