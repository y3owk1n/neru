# Mode handler — locking contract (deadlock hazard)

`modes.Handler` is split for compiler-enforced locking: the outer `Handler` owns `mu` and the exported entry points (`HandleKeyPress`, `ActivateMode`, `ExitMode`, …), each of which locks and delegates into the embedded `handlerState`, which carries all fields and lock-held methods and has no mutex. Modes are built on `*handlerState`, so calling a locking entry point from locked context is a compile error.

- Deferred callbacks (timers, goroutines) reach the lock via `handlerState.outer` — **never call it synchronously**; from a method running under `h.mu` it self-deadlocks.
- Lock order: `moveMonitorMu` → `h.mu` → `StyleResolver.mu`, never the reverse. Reading a Style under `h.mu` is safe because the resolver's read lock is taken and released by the reader and the resolver never calls back into the handler; handler context must never reach the resolver's `applyMu`, which is held across pushes into the render components. Since #1212 *every* one of those reads happens inside the overlay adapter — the handler holds no style source at all — so the edge is entirely `h.mu` → adapter → `StyleResolver.mu`, reached through a draw rather than by a mode asking for a Style. Any new mutex needs a stated position in that order.
- Don't hold `h.mu` across blocking calls (IPC, exec, channel sends, overlay draws, modal dialogs) or adapter calls that can synchronously call back into the handler. Overlay draws may block by contract (`internal/adapter/overlay/AGENTS.md`). Three kinds of call still reach the overlay under the lock and all are deliberate. **The hints surface**: since #1210 it goes through `ports.OverlayPort`, but it still draws under `h.mu`, because the hint manager's update callback fires from `SetHints`/`Reset`/`HandleInput`, which already hold it — that is `drawHints` (`hintdraw.go`), and with it `RefreshHintsForThemeChange`, `drawHintSearchInput`, `hideHintSearchInput` and `hintSearchBounds`, which reach the same surface from the same locked context. The first draw of an activation is a *transition*, so `ResizeToActiveScreen` → `Show` → `SwitchTo` run under `h.mu` too (`overlay/adapter.go`, `ShowFrame`) — which is what makes "nothing holding `renderMu` may take `h.mu`" and "macOS `Show` stays `dispatch_async`" load-bearing rather than incidental. `hintSearchBounds` and the grid surfaces both reach `StyleResolver.mu` through the adapter; that is the documented order, not an exception to it. **The grid surfaces**: since #1211 grid and recursive grid go through the same port, and like hints they draw under `h.mu` — activation hands over a Frame from locked context (`grid.go`, `recursive_grid.go`), and so do the per-keystroke updates, which run from the grid manager's update callback fired by `HandleInput` under the lock (`frames.go`). An activation runs the `ShowFrame` window sequence, and since #1213 so does a **screen change**: `RefreshGridForScreenChange` hands over a Frame, `RefreshRecursiveGridForScreenChange` does too, and `RefreshHintsForScreenChange` clears `hintsFrameOnScreen` so the `SetHints` callback shows rather than redraws — the display moved under the overlay, so resizing and re-showing is part of realizing the frame and no longer open-coded in `app/lifecycle.go`. A keystroke never runs it, including the one that leaves a subgrid — that is a `RedrawFrame`, and erasing the subgrid is the adapter's business. The screen-change callers are goroutines, never the main queue, and the one `dispatch_sync` inside `ShowFrame` (hiding the monitor-select panels) is gated on the picker being drawn, which no screen-change refresh can be. Nothing there computes a plan and draws after release, because there is nothing to release to: the whole activation is one locked entry point. Since #1212 the same is true of the last two surfaces: monitor-select hands over a Frame on activation, on every keystroke and on a theme change, and scroll hands over one on activation — all from locked context, and neither brings the shared window up. **Mode teardown**: `stopIndicatorPolling` hides each indicator and `performCommonCleanup` clears the frame, both of which take the Linux manager's `renderMu`. A monitor move clears the frame under `h.mu` too (`clearFrameForMonitorMove`), from `MoveMonitor`'s `moveMonitorMu`, which is the documented order and the reason that lock sits above `h.mu`. Note what that clear can reach on macOS: with monitor-select panels on screen it makes a **synchronous** hop to the main queue (`NeruHideMonitorSelectPanels` is a `dispatch_sync`), so `h.mu` is held across a main-thread round trip. That is safe only while nothing running on the main queue takes `h.mu` — the event tap only enqueues onto its dispatcher and the hotkey callback starts a goroutine — and any new main-queue callback that reaches the handler breaks it. That direction is safe because nothing holding `renderMu` ever takes `h.mu`: the overlay never calls into the app, and the handler is not an overlay subscriber. Lock order there is `h.mu` → `renderMu`, never the reverse. The indicator hide cannot move off the lock — it has to happen after the polling goroutine is joined, or a late tick puts the indicator back on screen.
- `ports.OverlayPort` carries four calls the handler must **never** make: `ApplyConfig`, `RefreshStyles`, `Destroy` and `SetHiddenInScreenShare`. They belong to the app's config, theme and shutdown paths, which run unlocked. Until #1213 the resolver lived on `App` and the compiler enforced this; now `RefreshStyles` from locked context would give `h.mu` → `StyleResolver.applyMu` → the render components, and `Destroy` is a `dispatch_sync` to the main queue under `h.mu`. Both are the inversions the lock order above forbids.
- The handler holds exactly one overlay reference, `overlayPort`. The Linux keyboard grab that used to reach the overlay package's singleton is `overlayPort.SetKeyboardCaptureEnabled`, gated as before on the **event tap** reporting overlay keyboard passthrough (#1213); no file here imports `internal/adapter/overlay`, and `internal/architecture/layering_test.go` fails if one does.
- **No method releases a lock it did not take** — every lock is released, via `defer`, by the method that took it; never unlock mid-method to make a blocking call safe. Instead compute a plan under the lock and have the lock-taking method execute it after release (`planIndicatorTick`/`drawIndicators` in `indicator_polling.go`), or hand the blocking call to a goroutine that re-enters through the outer locked surface guarded by the mode-session token (`requestScreenCapturePermissionAndResume` in `hints.go`).

The `Mode` interface is `Activate(modecmd.Activation)`, `HandleKey(string)`, `Exit()`, `ModeType()`; embed `baseMode` (`base.go`) for defaults and register in the handler's mode map. `Handler.ActivateMode` is the only activation entry point (`handler.go`).

Concurrency-sensitive changes need a test that fails under `-race`: `go test -race ./internal/app/modes/`. Run the `deadlock-reviewer` agent on the diff before opening a PR.
